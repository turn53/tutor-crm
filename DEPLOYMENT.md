# Запуск CRM на VPS

Рабочий экземпляр развёрнут на VPS: https://crm.my-tutorcrm.ru.
Инструкция ниже описывает также повторное развёртывание на чистом сервере.
Google Calendar и YouTube требуют OAuth-разрешений владельца аккаунта.
Проверки с имитацией API не заменяют проверку реального Google/Zoom на сервере.

## Что требуется от владельца

1. Создать аккаунт Beget или Timeweb Cloud и арендовать Ubuntu 24.04 LTS,
   2 CPU / 4 ГБ RAM / от 40–50 ГБ диска / публичный IPv4. Либо 4 CPU / 8 ГБ.
   Платная панель, отдельная БД и GPU сейчас не нужны.
2. Зарегистрировать домен на своё имя. Для CRM использовать поддомен `crm`.
   Название выбирает владелец. В DNS добавить A-запись `crm` на IPv4 сервера.
3. Предоставить IP и SSH-доступ по отдельному публичному ключу. Закрытый ключ,
   пароль от хостинга и платёжные данные в переписку не отправлять.
4. Создать проект Google Cloud, включить Google Calendar API и YouTube Data API v3,
   создать OAuth client типа Web application. Адрес возврата:
   `https://crm.ВАШ-ДОМЕН/oauth/google/callback` — точное значение также показано в CRM.
5. Сохранить Client ID и Client Secret в настройках CRM. Отдельно нажать
   «Подключить календарь» и «Подключить YouTube», войти в нужный Google-аккаунт.
   Для YouTube нужен созданный канал. Затем выбрать календарь и включить автоматику.

Для тестирования OAuth добавить свой аккаунт в test users. Режим Testing у внешнего
OAuth-приложения может ограничивать срок refresh token семью днями. Для постоянной
работы нужен соответствующий режим публикации приложения и, когда Google требует,
проверка разрешений. Нельзя обещать полностью автономную работу, пока это не проверено.

Новые непроверенные API-проекты YouTube могут загружать видео только с закрытым
доступом. Выбор «по ссылке» в CRM не отменяет ограничение Google: статус проверяется
после обработки. Для снятия ограничения может потребоваться аудит YouTube API.

## Схема доступа

Интернет → Caddy (HTTPS + логин/пароль) → CRM в закрытой Docker-сети.
Порт CRM 8765 наружу не опубликован. Приложение проверяет Host и отдельный секрет
прокси; настройки и базы в Docker-образ не копируются. Авторизация первого этапа —
стандартное окно логина браузера, один владелец CRM. Разные роли пользователей
и самостоятельные кабинеты учеников в текущую версию не входят.

## Команды для развёртывания

После подготовки VPS установить Docker Engine и Compose по официальной инструкции
для Ubuntu: https://docs.docker.com/engine/install/ubuntu/ . Открыть TCP 80 и 443;
SSH ограничить своим доступом. Не публиковать 8765. Убедиться, что из выбранного
региона доступны Zoom, OAuth Google, Calendar API и загрузки YouTube.

На ноутбуке: `python deploy/package.py` создаёт `.runtime/crm-deploy.tar.gz` только
с кодом. Перенести архив по SSH в `/opt/tutor-crm` и распаковать там. На сервере:

```sh
cd /opt/tutor-crm
sudo python3 deploy/setup_env.py
```

Скрипт запросит домен, логин и пароль (не показывает пароль), создаст `.env`
с хешем пароля и секретом прокси. Откажется перезаписывать существующий `.env`.

Перед окончательной миграцией остановить локальный процесс CRM и не вносить
правки на ноутбуке. Выполнить на ноутбуке:

```sh
python deploy/migrate.py export .runtime/migration-final
```

Каталог содержит персональные данные и секреты, переносить только по SSH.
Импорт на сервере не перезаписывает существующую базу:

```sh
sudo python3 deploy/migrate.py import /путь/к/migration-final
sudo docker compose config --quiet
sudo docker compose run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile
sudo docker compose up -d --build
sudo docker compose ps
```

Автоматические работники в миграционной копии выключены. До переключения:
сверить учеников, оплаты, начисления и конспекты; проверить доступ без пароля (должен
отклоняться), с паролем, с телефона через мобильную сеть; проверить HTTPS и экспорт.
Только затем включить Zoom, календарь и видео на сервере. Локальную автоматику
оставить выключенной: независимые рабочие базы не синхронизируются между собой.

## Поведение интеграций

- Календарь — источник времени: создавать/переносить события в Google Calendar.
  CRM загружает интервал 90 дней назад / 180 дней вперёд, включая отдельные повторения.
  Ученика/группу можно привязать к одному событию или всей серии. Неопознанные
  события не превращаются в начисления. Время в интерфейсе — московское.
- «Проведено» создаёт один урок, повторный клик не создаёт второй. При однозначном
  совпадении участника и времени (до 30 минут) Zoom дополняет тот же урок.
  Неоднозначные совпадения требуют проверки. Фиксированный месячный счёт не растёт
  от отметок уроков; поурочный месячный счёт пересчитывается. Способ расчёта задаётся
  для каждого месяца в финансах, автоматически на следующий месяц пока не переносится.
- Перенос/удаление календарного события после проведения не стирает финансовую
  историю: CRM показывает предупреждение. Для исправления факта проведения
  снять отметку или отменить занятие в CRM.
- Включённая публикация конспекта обновляет только блок CRM в описании события,
  с проверкой версии Google (ETag). Внутренние оценки и исходная сводка туда не идут.
  Конспект доступен всем, кто имеет доступ к описанию события. Уведомления гостям
  намеренно не запрашиваются (`sendUpdates=none`).
- Перенос видео работает отдельно от обработки конспекта. Для одного сегмента
  записи выбирается один MP4-ракурс, части после остановки/возобновления записи
  загружаются отдельно. Необработанная запись может ожидать сводку/идентификацию урока.
- По умолчанию видео закрытые. Файлы переносятся по одному, кусками по 8 МБ,
  с проверкой свободного диска. Лимит одного файла 8 ГБ, меняется `CRM_VIDEO_MAX_BYTES`.
  Перед повтором загрузки запрашивается подтверждённая позиция YouTube.
  Неопределённое состояние истёкшей сессии требует проверки канала перед повтором.
  Zoom автоматически не очищается. После статуса готовности проверить воспроизведение
  и только тогда удалять исходники вручную. Для нескольких частей проверить все части.
- CRM создаёт проверенную SQLite-копию ежедневно и хранит 14 копий в `server-data/backups`.
  Это копии на том же VPS: включить также резервирование провайдера. Секретные файлы
  и `.env` хранить отдельно в защищённой копии, не отправлять в репозиторий.

## Приёмка после подключения аккаунтов

Провести один тестовый урок с двумя участниками: событие Calendar → запись Zoom →
отчёт в CRM → отметка проведения → правильное начисление → конспект в Google →
запись на YouTube и просмотр владельцем. Проверить перенос следующего события,
отмену, исправление ошибочной оплаты, перезапуск VPS и восстановление копии.

Пока этот сценарий не выполнен, интеграции считаются подготовленными, а не проверенными
в реальной эксплуатации. На ноутбуке Docker Engine сейчас не запущен: сборка образа
и получение настоящего TLS-сертификата должны быть проверены на сервере.

## Обновления и восстановление

Перед обновлением сделать копию базы, сохранить предыдущий код. Развернуть новый код,
запустить тесты, пересобрать `docker compose up -d --build`. Том `server-data` сохраняется.
При восстановлении остановить CRM; восстановить базу и секреты из проверенной копии,
вернуть права UID 10001, запустить и сверить итоги. Не использовать `docker compose down -v`:
это удалит хранилище сертификатов Caddy. Не заменять работающую SQLite обычным копированием.

Источники: [Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server),
[YouTube upload](https://developers.google.com/youtube/v3/docs/videos/insert),
[resumable uploads](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol),
[Calendar events](https://developers.google.com/workspace/calendar/api/v3/reference/events/list),
[Caddy authentication](https://caddyserver.com/docs/caddyfile/directives/basic_auth).
