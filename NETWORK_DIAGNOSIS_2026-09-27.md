# OneDash: частичная передача HTTPS без VPN

## Подтверждённые результаты

Рабочая CRM: `crm.my-tutorcrm.ru`, OneDash `195.226.93.186`.
База остаётся в `/opt/tutor-crm/server-data/crm.sqlite3`.

Из обычного подключения тестового компьютера воспроизведена остановка передачи
после части HTTPS-ответа. Для диагностических сокетов Windows использованы
привязка к физическому IPv4-интерфейсу и IP_UNICAST_IF; системный VPN не отключался.
Отдельный исходный публичный IP подтверждён журналом сервера.

HTML имеет длину 61048 байт. В повторных прямых HTTP/1.1-проверках без сжатия
получалось 20931 байт, затем тайм-аут чтения. HTTP/2 также зависает. Через VPN
HTML и API загружаются целиком. Серверный tcpdump показывает повторные отправки
одних и тех же диапазонов TCP sequence без дальнейших подтверждений.
Точное место потери и конкретный оператор/механизм фильтрации не установлены.

Следующие диагностические изменения не восстановили полный цикл HTML + API:

- HTTP/1.1 вместо HTTP/2 и TLS 1.2 вместо стандартного согласования TLS;
- gzip: HTML 61048 -> 20214 байт, API 900764 -> около 91643 байт;
- MSS 1160 только для тестового клиента;
- временное перенаправление порта 8443 на тот же TLS-сервис для тестового клиента;
- отключение TSO/GSO на время теста;
- отсутствие SNI, с проверкой цепочки сертификата и имени в SAN.

Все временные настройки возвращены. Пользователь сообщил ухудшение после
включения сжатия, поэтому `encode zstd gzip` удалено и конфигурация перезагружена.
Оставлено только удаление чувствительных заголовков из стандартного журнала Caddy,
в дополнение к уже существующему обезличенному журналу доступа.

## Проверки и следующий шаг

Перед первым изменением создана онлайн-копия SQLite с integrity_check=ok.
Во время диагностики приложение и рабочая база не изменялись.
Конфигурация Caddy проверялась до загрузки; откат сжатия сверялся с локальным файлом.
Эквивалентность распакованных HTML/JSON проверена до отката; через VPN проверены
авторизация, защита токеном, шесть параллельных чтений и интеграции.

Нужна диагностика маршрута/фильтрации у OneDash. Черновик обращения подготовлен
локально, не отправлен. Новый IP или другой входной сервер следует сначала проверить
полной загрузкой HTML и API из проблемной сети и лишь затем переключать DNS.
Не запускать старую базу Beget как рабочую: после миграции появились новые записи.

Локальные диагностические инструменты и выводы: `.runtime/access-20260927`.
Серверные материалы: `/root/crm-migration/access-20260927`.
